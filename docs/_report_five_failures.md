**1. Complaints not escalated (Fix 1).** Case: complaint-01/03/04. The model apologised and offered to help but sometimes never called `escalate` ("Sure, I'll pass this to our team..." with `actions: []`), 0/3 baseline runs passing on complaint-04. Root cause: relying on the model to remember every time is fragile. Fix: a code-level safety net (`agent.py`) auto-calls `escalate` whenever a complaint/human-request intent (data-driven, `intents.py` + `lexicon.toml`) is detected and the model didn't call it itself this turn. Result: complaint pass rate 58.3% -> **100%** (`reports/runs/20260928-163524-fix5-6-7-combined/`).

**2. Unknown items substituted (Fix 3), plus the arith-01 resolver regression it exposed.** Case: unknown-01/03/04. "Do you make rabri?" answered with Kaju Katli's price as if it answered the question. Root cause: the prompt said to admit not knowing, but never forbade substituting a real, wrong product's price as a "helpful" answer. Fix: an explicit "NEVER substitute a different product's price or fact" rule with per-language examples. Result: unknown pass rate 27.8% -> **88.9%**. Verifying this fix's prompt changes exposed a *separate*, pre-existing bug: arith-01 (100% at baseline) regressed to 0% -- traced directly to `pricing._resolve_item` picking the wrong SKU on a tie ("diwali gift box" vs "gift box large" matched by character length, not word specificity). Fixed by rewriting alias matching to order-insensitive word-set comparison ranked by word count, plus a size-word disambiguation layer -- verified with 6 new unit tests; arith-01 restored (`reports/runs/20260928-165509-fix-resolver-verify/`).

**3. lead-03 invented "Mr. Patel" (Fix 5).** The model hallucinated a name, phone number and date **none of which the customer typed**, and never corrected it when the real customer's details arrived next turn. Root cause: `save_lead`'s arguments were trusted at face value. Fix: every name/phone/email argument must be grounded in text the customer actually wrote (whole-word match, casefold), plus a "lead nudge" that forces a `save_lead` attempt when the customer gives valid contact details and none has been saved yet. Result: lead pass rate 86.7% -> **100%** (final-2); the exact hallucination scenario is unit-tested (`test_name_grounding_rejects_hallucinated_name`).

**4. hinglish-04: an invented order, caused by our own Fix 6.** Fix 6 (forcing `calculate_order` whenever a "total" intent + quantity digit appears) fired on the bare number "7000" in a pure COD-limit question ("7000 ke order pe cash on delivery milega kya?"), and the model invented items ("Mixed Namkeen x10, Gulab Jamun x1") to justify a tool call the customer never asked for -- a regression Fix 6 itself introduced. Root cause: no check that a `calculate_order` call's items were things the customer actually asked for. Fix: item-argument grounding (reject any item not backed by a lexicon alias or literal SKU the customer wrote), plus narrowing the calc-nudge trigger to require a quantity attached to a product/unit word, not a bare number. Result: invented-amount rate dropped from the round-1 regression peak of 3.2% back to **1.4%** (final-2), with the exact scenario unit-tested (`test_item_grounding_rejects_unmentioned_item`, `test_no_calc_nudge_for_bare_number`).

**5. hindi-06: "2 पैक" priced as kg (Fix 7 -> Fix 9c -> the tool-call-leak guard).** "2 पैक चाहिए" (2 packs) was computed as `unit="kg"`, giving ₹1,360 instead of ₹740. **The prompt-only fix failed**: clarifying the tool schema's unit description didn't change the model's argument choice (confirmed by direct tracing -- identical wrong result after the change). The actual fix was code-side: an independent pack-quantity extraction from the customer's own words, rejecting a `calculate_order` call whose unit disagrees (Fix 9c) -- verified by unit test (`grand_total == 740`) and live re-run (2/3, up from 0/3). **Honest final state**: hindi-06 remains flaky in the submission run (1/3) -- not from the pack/kg bug (confirmed absent in every trace checked), but from the model occasionally failing to call the tool at all, including leaking its own tool-call JSON as reply text (`ordinal "calculate_order" को इस प्रकार संशोधित करें: {...}`). This new failure mode is what the Part 10A tool-call-leak guard (`guards.py`) targets -- a residual model-reliability limit on tool-call retry discipline, mitigated but not eliminated by a guard-and-retry layer around a small local model.
